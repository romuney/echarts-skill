# Proteus eCharts Builder

eCharts у нас НЕ рисует. Ему отдаётся пустой `option`, он служит только холстом.
Визуализация пишется вручную на HTML+CSS+SVG+JS и монтируется в ОТДЕЛЬНЫЙ overlay-div
поверх хоста. Данные приходят из SQL под графиком как глобальный массив `data`.

Каркас — `templates/TEMPLATE.chart.js`, БЛОКИ 1–7. Это единственный эталон: чистая
болванка без примеров графиков. Входной макет может быть любым — не ищи похожий пример
и не подгоняй задачу под знакомый тип графика.

# ЧТО ЧИТАТЬ И КОГДА

Контекст ограничен, а макет и JS могут быть огромными. Читай ТОЛЬКО то, что нужно
текущей задаче, и ровно один раз. Лишний файл — это минус сотни строк макета, которые
ты потом не сможешь удержать.

| Файл | Что внутри | Когда читать |
|---|---|---|
| `SKILL.md` (этот) | контракт, режимы, железные правила, workflow | всегда |
| `PATTERNS.md` | RETRO 1–26 каркаса и overlay + рецепты | всегда, ПЕРЕД первой строкой кода |
| `templates/TEMPLATE.chart.js` | эталонный каркас, БЛОКИ 1–7 | при создании нового `.chart.js` |
| `SQL.md` | политика «считает JS» + ClickHouse 24.8 + чек-лист Q | только если пишешь или правишь SQL |
| `TABLES.md` | pipeline таблиц, состояние, RETRO 27–40, чек-лист I | только если в макете таблица с поиском / сортировкой / пагинацией / экспортом / перестановкой колонок |
| `SELF_CHECK.md` | чек-лист сдачи, обязательное ядро | перед сдачей |
| `REGRESSION.md` | сценарный регресс интерактивных таблиц | перед сдачей, если читал `TABLES.md` |

| `smoke.mjs` | поведенческая проверка в браузере: что видно на экране | НИКОГДА не читай — только запускай, перед сдачей и при любом «не работает» |
| `retro-coverage.py` | карта: какие RETRO закрыты автопроверкой, а какие нет | только когда дорабатываешь сам скилл, не при сборке графика |

# ДВА РЕЖИМА РАБОТЫ

Определи режим ПЕРВЫМ действием и назови его вслух. Правила разные.

**РЕЖИМ A — новая визуализация** (нет `.chart.js` либо он пустая болванка).
Полный цикл: план → подтверждение → NOTES → блоки 1→7 → `validate.py` → `SELF_CHECK.md`.

**РЕЖИМ B — точечная правка** рабочего `.chart.js` по однозначной задаче
(«подкрась колонку», «почини sticky», «добавь колонку X»).
Плана и подтверждения НЕ жди — сразу минимальный diff. Но обязательны:
`node --check`, `python3 validate.py`, и регресс-смоук по затронутым функциям
(`REGRESSION.md`, только затронутые строки).
Задача неоднозначна или правка задевает больше двух функций — это РЕЖИМ A.

# КОНТРАКТ ФАЙЛОВ

| Файл | Роль | Право на правку |
|---|---|---|
| `<name>.html` | Макет-эталон: вёрстка, дизайн, состав элементов | ТОЛЬКО ЧТЕНИЕ |
| `<name>.data.sql` | Источник данных. Каждая выходная колонка = ключ в `data` | Правь ТОЛЬКО с явного «да» пользователя |
| `<name>.chart.js` | Единственный результат skill: отрисовка макета на данных SQL | Создавай блоками |
| `<name>.NOTES.md` | Рабочая память агента. В Proteus НЕ вставляется | Веди постоянно |
| `FIELDS.md` | Сдаточный документ: поля и ручные настройки Proteus | Заполняй в конце |

Правила связки:

1. Выходные поля SQL — это и есть массив `data` в JS. Других данных не существует.
2. Mock-данные в HTML-макете — заглушки. ЗАМЕНИ каждую на поле из SQL.
3. Данных в SQL НЕ ХВАТАЕТ → ОСТАНОВИСЬ и СПРОСИ: добавить поле в SQL или оставить
   значение статическим справочником из HTML. НЕ придумывай колонку и НЕ выкидывай
   элемент макета молча.
4. Поле не попадёт в `data`, пока пользователь ВРУЧНУЮ не добавит его в «Измерения».
   Поэтому любое предложение добавить или переименовать колонку сопровождай
   предупреждением: «эту колонку нужно вручную добавить в «Измерения», иначе в `data`
   её не будет». Имена совпадают ПОБУКВЕННО: SQL == `CFG.fields` == `FIELDS.md`.
5. Тип значения ≠ то, что видно в UI-таблице. `DATE`/`DATETIME` часто приходят
   epoch-числом. Всегда гони даты через `toDate` из БЛОКА 2.

# ЖЕЛЕЗНЫЕ ПРАВИЛА

1. **План до кода — в РЕЖИМЕ A.** Сначала нумерованный план: какие файлы, какие блоки,
   в каком порядке. Дождись подтверждения. Только потом пиши. В РЕЖИМЕ B плана нет.

2. **Считает JS, а не ClickHouse.** SQL отдаёт СЫРЫЕ строки нужной гранулярности.
   Все производные величины — суммы, доли, проценты, дельты, ранги, накопительные
   итоги, сортировка, форматирование — считаются в `buildModel()`. Базу не нагружаем.
   Перенести расчёт в SQL можно ТОЛЬКО спросив пользователя и предупредив про
   «Измерения» (КОНТРАКТ, п. 4). Границу «что всё-таки остаётся в SQL» и синтаксис
   ClickHouse смотри в `SQL.md` — читай его только когда реально трогаешь SQL.

3. **Память — на диске, а не в контексте.** Первым действием РЕЖИМА A создай
   `<name>.NOTES.md` из `templates/TEMPLATE.NOTES.md`. Это единственный источник
   правды по ходу работы: реестр макета, покрытые диапазоны, колонки SQL, решения,
   статус блоков. Пиши в него ДО следующего действия, а не «потом соберу».
   Держать реестр только в чате ЗАПРЕЩЕНО.

4. **HTML покрывается ПОЛНОСТЬЮ, но не держится в контексте.** Сначала РЕАЛЬНО
   выполни `wc -l <name>.html` и запиши полученное число в NOTES §2 как M.
   Не оценивай M на глаз и не бери его из последней прочитанной строки:
   `validate.py` сверяет M с файлом и роняет сдачу при расхождении.
   До 300 строк — читай целиком. Больше — читай диапазонами по ≤300 строк;
   после КАЖДОГО диапазона немедленно допиши NOTES §1 и §2 и только потом бери
   следующий. Не цитируй HTML в ответ — цитируй реестр. Забыл деталь — перечитай
   NOTES, а не HTML. Диапазоны в §2 обязаны покрыть 1..M без дыр.

   **Дочитывай до конца, особенно `<script>` макета.** Самое ценное обычно лежит
   в последней трети файла: mock-данные и референсная реализация. Именно там макет
   объявляет, какие поля и какую ФОРМУ данных он ждёт (`row.<поле>`,
   `data.filter(...)`, ключи мока). Выпиши это в NOTES §3 и сверь с колонками SQL
   ДО первой строки кода. Остановиться на середине макета и достроить модель
   по своему разумению — самая дорогая ошибка в этом скилле: она не ломает
   ни синтаксис, ни валидатор, и всплывает уже у пользователя.

5. **Код только модульно, с чекпоинтом.** НИКОГДА не генерируй `.chart.js` одним
   куском. Пиши по одному БЛОКУ за раз, по порядку 1→7. Блок сам по себе больше
   ~250 строк (обычно это БЛОК 5) — дели его на части по смыслу и проверяй каждую.
   ЧЕКПОИНТ после каждого куска, порядок жёсткий:
   (1) `node --check <file>.js` — нет `Syntax OK`, не продолжай;
   (2) строка в NOTES §5: `блок N | DONE | Syntax OK | строки a-b`;
   (3) в чате статус ≤3 строк: что сделано, что дальше, закрыто X из Y элементов реестра.
   Без всех трёх шагов следующий блок не начинается.

6. **Возобновление вместо перезапуска.** Контекст обрезан, сессия перезапущена или
   пользователь вернулся позже — НЕ начинай заново и НЕ перечитывай HTML. Прочитай
   `<name>.NOTES.md` целиком, найди первый пункт со статусом ≠ DONE, продолжай с него.

7. **Каркас копируется, не изобретается.** БЛОКИ 2, 6 и 7 берутся из шаблона: их
   структура, порядок и служебный код меняться не должны. Заполняются ТОЛЬКО помеченные
   `[ЗАПОЛНИ]` места (ключи состояния в БЛОКЕ 2, тело `renderTip()` и обработчики
   в БЛОКЕ 6). Всё остальное в этих блоках — дословно. Свободны `CFG` (1),
   `buildModel` (3), форматтеры (4) и разметка (5).

   `getTip()`, `showTip()`, `hideTip()` и `render()` — СЛУЖЕБНЫЕ. Не переписывай,
   не переименовывай и не пиши рядом свои версии: в них заперты инварианты,
   на которых ломались прошлые версии (видимость тултипа, клампинг по вьюпорту,
   пересборка разметки). Своя реализация тултипа «по образцу» — это RETRO 44:
   правило `opacity:0` из шаблона остаётся, а снятие теряется.
   Имена тоже часть контракта: по ним ищет `validate.py`, переименовал —
   проверка молча пропадает из отчёта.

   В папке уже есть работающий график? БЛОК 6 копируется ИЗ НЕГО целиком,
   меняются только содержимое тултипа и обработчики. Это дешевле и надёжнее,
   чем писать заново по памяти.

8. **ВОПРОС — КРАЙНЯЯ МЕРА, а не приветствие.** Сначала выведи всё, что выводится из
   макета и SQL. Спрашивай ТОЛЬКО то, без чего график ФИЗИЧЕСКИ не построится: нет
   числового поля под видимый элемент макета, два равнозначных поля-кандидата, прямое
   противоречие макета и SQL, либо нужен расчёт в SQL (правило 2). Одним сообщением,
   не больше 3 вопросов, с вариантами ответа.

   НИКОГДА не спрашивай:
   - **Про дату и период**, если в макете нет оси времени, тренда или переключателя
     гранулярности. График-СНИМОК на текущую дату — НОРМА и частый случай.
     Поставь `CFG.mode = 'snapshot'` и работай дальше.
   - **Про `id`, ключи, `data-*` атрибуты из макета.** Это внутренняя вёрстка:
     генерируй ключи сам из имён своих же строк. В SQL они не нужны.
   - **Про цвета, шрифты, отступы, тексты кнопок** — всё есть в макете. Скопируй.
   - **Про «какие ещё данные показать»** — показывай ровно то, что в макете.

9. **Правки точечные.** Рабочий код и макет не переписывай целиком — только diff.

10. **Машинная проверка обязательна.** Перед сдачей запусти
    `python3 validate.py <путь>.chart.js`. Вывод вставь в ответ КАК ЕСТЬ.
    Хотя бы один FAIL — работа НЕ СДАНА. Запрещено писать PASS по памяти или
    «на вид всё верно»: только реальный вывод скрипта. Ответ БЕЗ блока вывода
    скрипта тоже НЕ СДАН — пересказывать результат словами нельзя.
    В цикле сборки гоняй с `--quiet`: он печатает только проблемы.

    Но **FAIL — это ГИПОТЕЗА, а не приговор** (RETRO 42). Скрипт ищет подстроки
    и не понимает смысла. Открой указанное место и убедись, что баг реальный.
    Реальный — чини код. Ложное срабатывание — чини `validate.py` и скажи об этом
    вслух. НИКОГДА не переименовывай и не перекраивай рабочий код только ради
    того, чтобы проверка позеленела: так теряется и время, и контекст.

11. **Сдача через `SELF_CHECK.md`.** Таблица PASS/FAIL/N-A с доказательством
    `файл:строка`. Скрипт проверяет каркас, ты — соответствие макету и смысл данных.
    Есть FAIL — исправь и повтори.

12. **Поведенческая проверка обязательна.** `validate.py` смотрит на ФОРМУ кода
    и не видит экрана: график может пройти его целиком и не работать. Реальный
    случай — 45/47 PASS при полностью мёртвых тултипах (RETRO 44). Поэтому перед
    сдачей ОБЯЗАТЕЛЕН второй прогон:

        node smoke.mjs <путь>.chart.js

    Он монтирует чарт в поддельный хост Proteus и проверяет в настоящем браузере:
    смонтировался ли overlay, появляется ли тултип при наведении на каждый триггер,
    ВИДЕН ли он (включая проверку пикселями), гаснет ли, меняет ли клик разметку,
    переживает ли перезапуск скрипта, что показывает пустой `data`.
    Вывод вставляется в ответ КАК ЕСТЬ, как и вывод `validate.py`. Хотя бы один
    FAIL — работа НЕ СДАНА.

    Данные берутся из `<name>.mock.json` (массив строк в форме выдачи SQL), а если
    его нет — генерируются из `CFG.fields`. Автомок проверяет живость интерфейса,
    а не правильность цифр: если поведение зависит от значений, положи мок руками.

    **Нет `playwright` — это НЕ провал и НЕ повод остановить сдачу.** Коды возврата
    разные и путать их нельзя: `1` — проверка провалена, работа не сдана; `2` —
    проверка не запускалась, сдача идёт дальше на статических проверках. Порядок
    действий при коде 2:

    1. проставь в отчёте `B1`–`B5` со статусом `N/A` и причиной «нет playwright» —
       строки должны БЫТЬ, иначе Z6 не найдёт ID и уронит сдачу;
    2. скажи пользователю прямо, одной строкой: поведенческая проверка не
       выполнялась, экрана никто не видел;
    3. предложи включить её одной командой:
       `npm i -D playwright && npx playwright install chromium`;
    4. **сам не ставь.** Установка пакета меняет чужую машину — только с явного
       «да». Отказался или промолчал — работаешь дальше, не возвращаясь к вопросу.

    Чего делать НЕЛЬЗЯ: писать «B: НЕ ПРОВЕРЕНО» вместо строк с ID, объявлять
    поведение проверенным на основании чтения кода, и наоборот — блокировать
    сдачу из-за отсутствующего инструмента.

13. **Не подгоняй код под проверку.** Заглушка, поставленная «чтобы позеленело»,
    гасит сигнал и оставляет баг — а потом выглядит как доказательство, что всё
    в порядке (RETRO 45). Проверка описывает ПОВЕДЕНИЕ, а не текст файла.
    Не проходит — либо чини поведение, либо чини саму проверку и скажи об этом
    вслух. Третьего варианта нет. `validate.py` (H2) ловит такие правки
    по комментариям и роняет сдачу.

Все известные падения — `PATTERNS.md` (каркас, overlay, тултип) и `TABLES.md`
(поиск, сортировка, пагинация, экспорт). Читай ПЕРЕД кодом.

# WORKFLOW РЕЖИМА A

## ШАГ 0. Разведка

Сделай `ls` папки ДО любых действий.

- **Макета нет** → ШАГ 1 (болванки).
- **Макет и/или SQL есть** → прочитай SQL целиком, HTML по правилу 4 → ШАГ 2.
- **Папки нет** → спроси имя/путь, создай, дальше ШАГ 1.
- **Есть `<name>.NOTES.md` с незакрытыми пунктами** → это возобновление (правило 6).

## ШАГ 1. Создание болванок

Скопируй из `templates/` в папку проекта, переименовав в `<name>`:
`<name>.html`, `<name>.data.sql`, `<name>.chart.js`, `<name>.NOTES.md`, `FIELDS.md`.

Болванки остаются ПУСТЫМИ. Ничего не догадывай: не выдумывай поля в `CFG.fields`,
не заполняй таблицу `FIELDS.md`, не придумывай макет и SQL.

Проверь болванку: `python3 validate.py <name>.chart.js --template`.
Флаг `--template` ждёт ПУСТОЙ `CFG.fields` — если там что-то есть, ты выдумал поля.

Затем СТОП и сообщи: «болванки готовы, пришли HTML-макет и SQL».

## ШАГ 2. Перенос макета в JS

1. Покрой HTML диапазонами по правилу 4 → NOTES §1 (реестр элементов и все
   mock-значения) и §2 (покрытие). В контексте держи NOTES, не HTML.
2. Прочитай SQL → NOTES §3: точный список выходных колонок и их типы. Это и есть
   ключи объектов в `data`. Их же запиши в `CFG.fields`.
3. Сопоставь реестр макета с колонками SQL. Нехватка → вопрос (КОНТРАКТ, п. 3),
   ответ и решение → NOTES §4.
4. Перенеси CSS макета в `buildCSS()`, префиксовав КАЖДЫЙ селектор через `CFG.ns`.
   Цвета, шрифты и отступы вынеси в `CFG.colors/fonts/spacing`.
5. Перенеси разметку макета в `buildHTML()` конкатенацией строк, данные — через `esc()`.
6. Напиши `buildModel()` под фактические поля: здесь считается ВСЁ производное
   (правило 2). Делегированные обработчики навесь ОДИН РАЗ СНАРУЖИ `render()`;
   внутри `render()` — только разметка и `renderTip()`.
7. Заполни `FIELDS.md`: точные имена, типы, чек-лист ручных настроек Proteus.
8. Запусти `python3 validate.py <name>.chart.js` и почини все FAIL.
9. Запусти `node smoke.mjs <name>.chart.js` и почини все FAIL. Это разные
   проверки: первая смотрит на код, вторая — на экран. Зелёная первая при
   красной второй означает ровно одно — график не работает.
10. Прогони `SELF_CHECK.md` — он покрывает то, что скрипты проверить не могут:
   соответствие макету, полноту реестра, смысл данных. Без полного PASS НЕ СДАНО.

Шаги 4–6 идут по правилу 5: блок → чекпоинт → блок. Не «напишу всё, потом проверю».

# КАК ПЕРЕНОСИТЬ ЛЮБОЙ HTML

| В макете | В `.chart.js` |
|---|---|
| `<style>` или внешний CSS | строки в `buildCSS()`, каждый селектор с префиксом `CFG.ns` |
| глобальные селекторы (`div`, `table`, `*`) | только `.<ns>-root div`, `.<ns>-root *` |
| `id="..."` + `getElementById` | классы и `overlay.querySelector('.<ns>-...')` |
| инлайн `style="..."` на динамике | оставляй инлайн: ширина бара, цвет ячейки |
| SVG | переносится как есть, внутрь `buildHTML()` |
| `<script>` в макете | логика переезжает в `render()`, обработчики — после `innerHTML` |
| тултип внутри контейнера | в `body`, `position:fixed`, стили дублируются инлайн |
| mock-числа и подписи | поля из `data` через `CFG.fields` |
| текстовые константы интерфейса | `CFG.text` |

# СИНТАКСИС И ОКРУЖЕНИЕ JS

Запрещено: backticks и template-literals, стрелочные функции, `let`/`const`,
`document.getElementById`, `console.log` в итоговом файле, внешние библиотеки,
`import`/`require`, `fetch`, любое чтение DOM вне своего overlay.

Обязательно: `var`, `function`, конкатенация строк, `option` глобально в самом конце,
`try/catch` вокруг монтажа с выводом ошибки текстом в overlay.

Скрытие элементов — только `style.display` или `style.opacity`. Атрибут `hidden`
и класс-переключатель без инлайн-стиля ненадёжны.

Спрятал ДВУМЯ свойствами — снимай ОБА. Правило `.<ns>-tip{display:none;opacity:0}`
и показ, снимающий один `display`, дают полностью невидимый узел при верных
событиях, координатах и тексте: ни ошибки, ни пустого экрана (RETRO 44).
Поэтому видимостью тултипа управляют ТОЛЬКО служебные `showTip()/hideTip()`
из шаблона — своих `style.opacity` для тултипа не пиши.

Состояние только в `window.__pvtState[CFG.ns]` — Proteus перезапускает скрипт на каждой
перерисовке, локальные переменные теряются. Глобальные слушатели (`window`, `document`)
при перезапуске накапливаются — вешай их через `state`-флаг, как в шаблоне.

СУБД — ClickHouse 24.8.15.1, и её диалект узкий: `lag`/`lead` там НЕТ, есть
`lagInFrame`/`leadInFrame`. Пишешь SQL — сначала открой `SQL.md`. Не пишешь — не читай.

# РУЧНЫЕ НАСТРОЙКИ PROTEUS

Skill не умеет настраивать UI. Измерения, сортировка, упорядочивание, лимит строк,
пагинация и фильтры выставляются руками. Выпиши их в `FIELDS.md`.
Если JS опирается на порядок строк — всё равно делай явный `sort` в `buildModel()`.
