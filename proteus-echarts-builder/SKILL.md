# Proteus eCharts Builder

eCharts у нас НЕ рисует. Ему отдаётся пустой `option`, он служит только холстом.
Визуализация пишется вручную на HTML+CSS+SVG+JS и монтируется в ОТДЕЛЬНЫЙ overlay-div
поверх хоста. Данные приходят из SQL под графиком как глобальный массив `data`.

Каркас лежит в `templates/TEMPLATE.chart.js` — БЛОКИ 1-7. Это единственный эталон.
Шаблон — чистая болванка без примеров графиков: в нём задан ТОЛЬКО каркас.
Не ищи похожий пример и не подгоняй задачу под тип графика — входной макет может быть любым.

## КОНТРАКТ ТРЁХ ФАЙЛОВ

В Proteus вставляются три отдельные сущности. Роли жёсткие:

| Файл | Роль | Право на правку |
|---|---|---|
| `<name>.html` | Макет-эталон: вёрстка, дизайн, структура, состав элементов | ТОЛЬКО ЧТЕНИЕ |
| `<name>.data.sql` | Источник данных. Каждая выходная колонка = ключ в `data` | Пиши по согласованию |
| `<name>.chart.js` | Единственный результат skill: отрисовка макета на данных SQL | Создавай блоками |

Правила связки:

1. Выходные поля SQL — это и есть массив `data` в JS. Других данных не существует.
2. Mock-данные в HTML-макете — заглушки. ЗАМЕНИ каждую на поле из SQL.
3. Если данных в SQL НЕ ХВАТАЕТ — ОСТАНОВИСЬ и СПРОСИ: добавить поле в SQL
   или оставить значение статическим справочником из HTML.
   НЕ придумывай колонку и НЕ выкидывай элемент макета молча.
4. Поле не попадёт в `data`, пока пользователь вручную не добавит его в «Измерения».
   Имена совпадают ПОБУКВЕННО: SQL == `CFG.fields` == `FIELDS.md`.
5. Тип значения ≠ то, что видно в UI-таблице. `DATE`/`DATETIME` часто приходят
   epoch-числом. Всегда гони даты через `toDate` из БЛОКА 2.

## ЖЕЛЕЗНЫЕ ПРАВИЛА

1. **План до кода.** Сначала нумерованный план: какие файлы, какие блоки, в каком
   порядке. Дождись подтверждения. Только потом пиши.
2. **Код только модульно.** НИКОГДА не генерируй `.chart.js` одним куском.
   Пиши по одному БЛОКУ за раз, по порядку 1→7. После КАЖДОГО блока:
   `node --check <file>.js`. Нет `Syntax OK` — не продолжай.
3. **Каркас копируется, не изобретается.** БЛОКИ 2 (вход/состояние/хелперы),
   6 (монтаж) и 7 (`option`) берутся из шаблона дословно. Импровизация допустима
   только в `CFG` (1), `buildModel` (3), форматтерах (4) и разметке (5).
4. **HTML читается ПОЛНОСТЬЮ.** Большой макет читай итеративно по частям, но перед
   написанием JS выпиши РЕЕСТР макета: все блоки, кнопки, дропдауны, колонки,
   тултипы, состояния. Реестр держи перед глазами до конца — ни один элемент не теряется.
5. **ВОПРОС — КРАЙНЯЯ МЕРА, а не приветствие.** Сначала выведи всё, что
   выводится из макета и SQL. Спрашивай ТОЛЬКО то, без чего график
   ФИЗИЧЕСКИ не построится: нет числового поля под видимый элемент макета,
   два равнозначных поля-кандидата, прямое противоречие макета и SQL.
   Одним сообщением, не больше 3 вопросов, с вариантами ответа.

   НИКОГДА не спрашивай:
   - **Про дату и период**, если в макете нет оси времени, тренда или
     переключателя гранулярности. График-СНИМОК на текущую дату — НОРМА
     и частый случай. Поставь `CFG.mode = 'snapshot'` и работай дальше.
   - **Про `id`, ключи, `data-*` атрибуты из макета.** Это внутренняя верстка:
     генерируй ключи сам из имён своих же строк. В SQL они не нужны.
   - **Про цвета, шрифты, отступы, тексты кнопок** — всё есть в макете. Скопируй.
   - **Про «какие ещё данные показать»** — показывай ровно то, что в макете.
6. **Правки точечные.** Рабочий код и макет не переписывай целиком — только diff.
7. **Машинная проверка обязательна.** Перед сдачей запусти
   `python3 validate.py <путь>.chart.js`. Вывод вставь в ответ КАК ЕСТЬ.
   Хотя бы один FAIL — работа НЕ СДАНА. Запрещено писать PASS по памяти Ответ БЕЗ блока вывода
   скрипта тоже НЕ СДАН: пересказывать результат словами запрещено.
   или «на вид всё верно»: только реальный вывод скрипта.
8. **Сдача через `SELF_CHECK.md`.** Таблица PASS/FAIL с доказательством `файл:строка`.
   Скрипт проверяет каркас, ты — соответствие макету и смысл данных.
   Есть FAIL — исправь и повтори.

Все известные падения и их причины — таблица RETRO в `PATTERNS.md`. Прочитай ПЕРЕД кодом.

# WORKFLOW

Скилл работает В ДВА ШАГА. Не прыгай сразу во второй.

## ШАГ 0. Разведка

Сделай `ls` папки ДО любых действий.

- **Макета нет** → ШАГ 1 (болванки).
- **Макет и/или SQL есть** → прочитай их полностью → ШАГ 2.
- **Папки нет** → спроси имя/путь, создай, дальше ШАГ 1.

## ШАГ 1. Создание болванок

Скопируй из `templates/` в папку проекта, переименовав в `<name>`:
`<name>.html`, `<name>.data.sql`, `<name>.chart.js`, `FIELDS.md`.

Болванки остаются ПУСТЫМИ. Ничего не догадывай: не выдумывай поля в `CFG.fields`,
не заполняй таблицу `FIELDS.md`, не придумывай макет и SQL.

Проверь болванку: `python3 validate.py <name>.chart.js --template`.
Флаг `--template` ждёт ПУСТОЙ `CFG.fields` — если там что-то есть, ты выдумал поля.

Затем СТОП и сообщи: «болванки готовы, пришли HTML-макет и SQL».

## ШАГ 2. Перенос макета в JS

1. Прочитай HTML полностью → выпиши реестр элементов и все mock-значения.
2. Прочитай SQL → выпиши точный список выходных колонок и их типы.
   Это и есть ключи объектов в `data`. Запиши их в `CFG.fields`.
3. Сопоставь реестр макета с колонками SQL. Нехватка → вопрос (КОНТРАКТ, п.3).
4. Перенеси CSS макета в `buildCSS()`, префиксовав КАЖДЫЙ селектор через `CFG.ns`.
   Цвета, шрифты и отступы вынеси в `CFG.colors/fonts/spacing`.
5. Перенеси разметку макета в `buildHTML()` конкатенацией строк, данные — через `esc()`.
6. Напиши `buildModel()` под фактические поля. Делегированные обработчики
   навесь ОДИН РАЗ СНАРУЖИ `render()`; внутри `render()` — только разметка и `renderTip()`.
7. Заполни `FIELDS.md`: точные имена, типы, чек-лист ручных настроек Proteus.
8. Запусти `python3 validate.py <name>.chart.js` и почини все FAIL.
9. Прогони весь `SELF_CHECK.md` — он покрывает то, что скрипт проверить не может:
   соответствие макету, полноту реестра, смысл данных. Без полного PASS НЕ СДАНО.

# КАК ПЕРЕНОСИТЬ ЛЮБОЙ HTML

Макет может быть любым. Правила переноса одни и те же:

| В макете | В `.chart.js` |
|---|---|
| `<style>` или внешний CSS | строки в `buildCSS()`, каждый селектор с префиксом `CFG.ns` |
| глобальные селекторы (`div`, `table`, `*`) | только `.<ns>-root div`, `.<ns>-root *` |
| `id="..."` + `getElementById` | классы и `overlay.querySelector('.<ns>-...')` |
| инлайн `style="..."` на динамике | оставляй инлайн: ширина бара, цвет ячейки |
| SVG | переносится как есть, внутрь `buildHTML()` |
| `<script>` в макете | логика переезжает в `render()`, обработчики — после `innerHTML` |
| тултип внутри контейнера | в `body`, `position:fixed`, стили дублируются инлайн |
| mock-числа и подписи | поля из `data` через `CFG.fields` |
| текстовые константы интерфейса | `CFG.text` |

# СИНТАКСИС И ОКРУЖЕНИЕ

Запрещено: backticks и template-literals, стрелочные функции, `let`/`const`,
`document.getElementById`, `console.log` в итоговом файле, внешние библиотеки,
`import`/`require`, `fetch`, любое чтение DOM вне своего overlay.

Обязательно: `var`, `function`, конкатенация строк, `option` глобально в самом конце,
`try/catch` вокруг монтажа с выводом ошибки в `option.graphic`.

Скрытие элементов — только `style.display` или `style.opacity`. Атрибут `hidden`
и класс-переключатель без инлайн-стиля ненадёжны.

Состояние только в `window.__pvtState[CFG.ns]` — Proteus перезапускает скрипт на каждой
перерисовке, локальные переменные теряются.

# РУЧНЫЕ НАСТРОЙКИ PROTEUS

Skill не умеет настраивать UI. Измерения, сортировка, упорядочивание, лимит строк,
пагинация и фильтры выставляются руками. Выпиши их в `FIELDS.md`.
Если JS опирается на порядок строк — всё равно делай явный `sort` в `buildModel()`.
